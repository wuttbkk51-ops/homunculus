# เริ่มออกแบบซอฟต์แวร์จากอะไร

อ่านไฟล์นี้เมื่อ user ยังไม่ได้ระบุว่าระบบทำอะไร หรือกำลังจะเริ่มโปรเจกต์ใหม่
(เขียนอธิบายเป็นไทย แต่ศัพท์เทคนิคคงเป็นภาษาอังกฤษ)

เริ่มจาก **problem และ user** ก่อนเทคโนโลยีเสมอ

## ลำดับ

1. **Problem**: เขียนเป็นประโยคเดียวว่า "ใครเดือดร้อนกับอะไร" ถ้าเขียนไม่ได้ แปลว่ายังไม่เข้าใจพอ
2. **User และงานที่ทำ**: ใครใช้ (admin, พนักงาน, ลูกค้า) เขียนเป็น use case สั้นๆ 3-5 ข้อ
3. **Data หลัก**: ระบบจัดการ data อะไร และสัมพันธ์กันอย่างไร (data เปลี่ยนยากกว่าโค้ด จึงคิดก่อนหน้าจอ)
4. **MVP**: ชุดความสามารถเล็กที่สุดที่แก้ problem ข้อ 1 ได้ **และเขียนสิ่งที่ไม่ทำไว้ด้วย**
5. **Constraint**: จำนวน user, ต้องใช้ offline ไหม, ระบบที่ต้องเชื่อม, งบและเวลา, ทักษะของทีม
6. **แบ่ง module**: ตามหน้าที่ แล้วกำหนด interface ระหว่างกัน
7. **เลือก stack และโครงสร้าง**: มาเป็นขั้นสุดท้าย ตัดสินจากข้อ 5
8. **ทำ vertical slice**: flow เดียวให้ครบทุก layer แล้วค่อยขยาย

## วิธีถาม user

ถ้าข้อมูลไม่ครบ ให้ถามรวมครั้งเดียว ไม่เกิน 3 ข้อ เลือกข้อที่เปลี่ยนการออกแบบมากที่สุด:
- problem และ user หลักคืออะไร
- data หลักมีอะไรบ้าง
- constraint สำคัญ (จำนวน user, ต้องเชื่อมระบบอื่นไหม)

ถ้า user ตอบไม่ครบ ให้ตั้งสมมติฐานแล้วระบุไว้ชัดๆ ในสรุป อย่าหยุดรอ

## กับดักที่เจอบ่อย

- เลือก framework หรือ library ก่อนเข้าใจ problem
- ออกแบบเผื่ออนาคตที่ยังไม่มี user จริง
- วาดหน้าจอก่อนคิด data แล้วต้องรื้อ schema
- ไม่เขียนสิ่งที่ "ไม่ทำ" ทำให้ขอบเขตบวม

## เอกสารขั้นต่ำ (1 หน้า)

problem, user, use case หลัก 3-5 ข้อ, data หลัก, สิ่งที่ไม่ทำ แล้วใช้เป็นฐานเขียน `AGENTS.md`

## โครงสร้างที่ต่อจากขั้นตอนนี้

- root `AGENTS.md`: stack, คำสั่งหลัก, กฎทุกงาน, ตารางบอกว่า "งานที่ทำ → ไฟล์กฎที่ต้องอ่าน"
- ไฟล์กฎแยกตามหัวข้อใน `.agents/rules/` (data-model, auth, ui-role)
- กฎต้องเป็นคำสั่งที่ตรวจได้ ("ห้ามมี query ใน Controller" ดีกว่า "เขียนโค้ดให้สะอาด")
